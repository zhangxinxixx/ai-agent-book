# 实验 4-2：Perception Tools + MCP 实验总结

## 1. 实验目标

验证 Perception Tools MCP Server 的最短协议链是否能在当前项目环境中工作：

```text
启动 Server
→ initialize
→ tools/list
→ tools/call(file_reader)
→ 返回 Tool Result
```

本轮是机制观察与离线冒烟，不是 Agent 自主工具选择实验，也不是 127 个工具的完整验收。

## 5. 实验说明了什么

1. 当前项目的 MCP v2 Client 与 Server 可以通过 stdio 建立会话。
2. Tool Schema 可以通过 `tools/list` 被统一发现。
3. Client 不需要导入 `read_file` 实现，只需按 Schema 发送 `tools/call`。
4. Tool Result 可以通过同一协议返回，成为上层 Agent 可使用的 Observation。
5. MCP 标准化通信和能力暴露，但不负责选择工具或进行 LLM 推理。

## 6. 与实验 4-4 的关系

| 4-2 Perception Tools + MCP | Tool 怎样通过统一协议被发现、调用并返回 Observation |

组合主链：

```text
Agent Decision
→ MCP Client
→ MCP Server
→ Guard
→ Tool Executor
→ External Environment
→ Tool Result
→ Observation
```

## 7. 不能从本轮推出什么

- 不能证明 127 个工具当前全部可调用。
- 不能证明任何公开 API、私有数据或 Vision Provider 当前可用。
- 不能证明 LLM 会选择正确工具或构造正确参数。
- 不能把历史 validation 的 126 工具 catalog 当成当前 127 工具的完整证据。
- 不能把自动冒烟完成等同于学习者已经掌握或亲自复现。

## 8. 已知证据差异

1. 当前源码和冒烟返回 127 个工具；历史 campaign 与保留测试记录 126 个。
2. 旧 `INDEX.md` / `PROJECT_SUMMARY.md` 中仍有 18 工具的早期统计，不代表当前 catalog。
3. 历史 `latest.json` 指向的 summary 内部仍写 `experiment: "4-1"`，且 catalog 缺少足以独立重算协议 gate 的版本字段。
4. 历史 manifest 在当前 Windows checkout 上无法完整通过哈希复核，因此只作为历史内容，不作为当前完整性证明。
