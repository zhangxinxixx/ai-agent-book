# 实验 4-2：Perception Tools + MCP 学习笔记

![感知工具静态架构图](assets/感知工具静态架构图.png)

> 学习目标：先看懂 MCP 怎样统一“工具发现、结构化调用和结果返回”，暂时不把注意力分散到天气、股票、OCR、Calendar 等具体后端。

## 1. 这一实验接在 4-4 后面学什么

实验 4-4 关注：

```text
Agent 已经决定行动后，工具怎样安全执行。
```

实验 4-2 关注：

```text
大量外部工具怎样用统一协议提供给 Agent。
```

两者组合后，完整链路是：

```text
LLM / Agent Decision
→ Tool Call
→ Agent Harness
→ MCP Client
→ MCP Server
→ Guard
→ Tool implementation
→ External Environment
→ Tool Result
→ Observation
→ 下一步 Decision
```

MCP 只标准化中间的通信与工具契约，不替 Agent 思考，也不等于具体 Tool。

## 2. Perception Tool 是什么

Perception Tool 主要从外部世界取得信息：

| 类型 | 当前项目示例 | 主要作用 |
| --- | --- | --- |
| 文件感知 | `file_reader`, `grep`, `directory_list` | 读取文件或目录状态 |
| 网络搜索 | `web_search`, `wikipedia_search`, `arxiv_search` | 获取公开信息 |
| 公开数据 | `weather`, `stock_price`, `currency_converter` | 查询外部数据源 |
| 多模态 | `document_reader`, `image_ocr`, `video_parser` | 把文档、图像、音视频转换成结构化 Observation |
| 私有数据 | `calendar_events`, `notion_search` | 在授权后读取个人或组织数据 |

感知工具并不天然等于“无风险”。读取范围、私有凭据、网络内容、超时和路径仍需要 Guard；当前项目甚至包含受限的 copy/move/delete，用于验证统一 MCP Server 的安全边界。

## 3. MCP 的三个角色

| 角色 | 含义 | 本轮实际对应 |
| --- | --- | --- |
| Host | 运行 Agent 或工具 Harness 的应用 | 冒烟测试没有 LLM Host，只有 `smoke_test_mcp_v2.py` 测试 Harness |
| Client | 建立连接、发现工具、调用工具、接收结果 | `mcp.Client` + `stdio_client` |
| Server | 暴露工具 Schema 并分派执行 | `src/main.py` 中的 `MCPServer("perception-tools")` |

概念上的 Agent Host 可以是 Codex、Claude Desktop、Cursor 或自建 Agent；但当前冒烟脚本没有模型决策，不要把“概念架构”误写成“本轮实际运行了 LLM”。

## 4. 第一遍只记三个动作

### 4.1 `initialize`

Client 进入 `Client(stdio_client(parameters))` 上下文时自动建立连接并协商协议。当前实测协议版本是 `2026-07-28`。

### 4.2 `tools/list`

Client 请求 Server 的工具目录，返回每个工具的：

```text
name
description
input schema
```

这一步是 Tool Discovery，没有执行具体工具。2026-09-22 当前冒烟发现 127 个唯一工具。

### 4.3 `tools/call`

Client 发送工具名和结构化参数：

```python
await client.call_tool(
    "file_reader",
    arguments={
        "file_path": ".../requirements.txt",
        "max_length": 2000,
    },
)
```

Server 校验参数、执行 `file_reader`，再把结果封装成 MCP Result 返回 Client。

## 5. MCP 与 Tool Calling 的关系

没有 MCP 时：

```text
LLM Tool Call
→ Harness 自己适配具体 Tool
```

加入 MCP 后：

```text
LLM Tool Call
→ Harness
→ MCP Client
→ MCP Server
→ Tool
```

所以：

| 对象 | 责任 |
| --- | --- |
| LLM / Agent | 决定是否需要工具、选择哪个工具、构造什么参数 |
| MCP | 描述工具、传输调用、返回结果 |
| Tool | 实际读取文件、访问 API 或处理媒体 |
| Harness | 把模型决策转成 MCP 调用，并把 Observation 送回运行状态 |

当前冒烟脚本用固定的 `file_reader` 代替 LLM 决策，只验证 MCP 最短路径。

## 6. stdio 是什么

`stdio` 是进程间传输方式。Client 启动：

```text
当前 Python解释器 src/main.py
```

然后通过标准输入和标准输出交换 MCP 消息：

```text
smoke_test_mcp_v2.py
        │
        │ stdin / stdout
        ▼
src/main.py MCP Server
```

MCP 不等于 HTTP。协议可以使用不同 Transport，本实验第一遍只需要理解 stdio。

## 7. State / Action / Observation / Decision / Guard

| 抽象 | 当前冒烟中的真实对应 |
| --- | --- |
| State | Client 连接状态、协商后的协议、已发现的 Tool Schemas |
| Action | `call_tool("file_reader", arguments=...)` |
| Observation | `file_reader` 返回的文件内容与 MCP Result |
| Decision | 当前脚本固定选择 `file_reader`；没有 LLM Policy |
| Harness | `smoke_test_mcp_v2.py` + MCP Client |
| Environment | 本地 `requirements.txt` |
| Guard | SDK major version、协议版本、工具存在性、Schema、路径和 `result.is_error` 检查 |
| Verifier | 冒烟脚本中的显式断言；完整 campaign 另由 `derive_acceptance()` 验收 |

## 8. 第一轮实际运行结果

2026-09-22 使用实验自己的 `.venv` 执行：

```powershell
.\.venv\Scripts\python.exe .\smoke_test_mcp_v2.py
```

结果：

```text
MCP SDK       2.2.0
协议版本      2026-07-28
Server        perception-tools
发现工具数    127
tools/call    file_reader 成功
Observation   requirements.txt，共 974 个字符
```

这次运行只证明：

1. Server 可以由 Client 通过 stdio 启动。
2. initialize 协商成功。
3. `tools/list` 能返回当前 catalog。
4. `file_reader` 的一次 `tools/call` 能返回结果。

它没有证明 127 个工具全部可用，也没有运行任何 Agent、公开 API、Vision、Calendar 或 Notion。

## 9. 推荐阅读顺序

1. `smoke_test_mcp_v2.py`：先看最短协议链。
2. `src/main.py`：看 Server 初始化、Tool 注册和 stdio 启动。
3. `src/filesystem_tools.py::read_file`：看一次具体 Tool 实现。
4. `实验 4-2 执行流程.md`：按真实行号跟完整调用顺序。
5. `run_experiment_4_2.py`：最后再看 28 cases、receipts 与验收门禁。

第一遍先不要从 `expanded_catalog.py` 的 70 个扩展工具、网络 Provider 或私有凭据开始。

2. Host、Client、Server 分别负责什么？
3. `tools/list` 为什么不是工具执行？

5. 当前冒烟中谁决定调用 `file_reader`？
6. MCP Server 是否负责 LLM 推理？

## 11. 一句话总结

> 实验 4-2 的核心不是“怎样查天气”，而是理解 Agent Runtime 怎样通过 MCP 统一发现和调用外部能力，并把 Tool Result 作为 Observation 交给下一步决策。
