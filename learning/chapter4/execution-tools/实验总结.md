# 实验 4-4：Execution Tools + MCP 实验总结

## 本次完成了什么

本实验核对了执行工具从请求到真实副作用的完整路径：调用者提交 Tool Call，Harness 先经过 Guard 做路径、语法、危险模式和超时检查，再执行文件、代码或 Shell 工具，最后把 `success`、`returncode`、`stdout/stderr` 等结果整理成 Observation。

## 当前验证结果

- `cli.py demo` 严格离线运行成功。
- 文件写入、语法拦截、代码执行、Shell 校验和长输出持久化均得到实际结果。
- 危险命令被拒绝，没有产生副作用。
- 当前自动测试结果：`63 passed in 2.15s`。

## 对 Tool Calling 的理解

一次完整的 Tool Calling 不是模型“自己执行函数”，而是：

```text
判断需要工具
-> 生成结构化 tool_call
-> Harness 校验
-> 调用工具
-> 获取 Tool Result
-> 作为 Observation 回传模型
-> 模型生成回答或继续调用工具
```

本项目验证了中间的执行基础设施，没有实现前后的 LLM 自主决策循环。因此不能把固定 demo 说成“Agent 已经自主完成完整任务”。

## 关键收获

1. Tool Schema 是模型与真实程序之间的接口契约。
2. Guard 负责执行前控制风险，Verifier 负责执行后核验证据。
3. `success=true` 只说明一次调用成功，不等于业务目标已经完成。
4. 长输出需要摘要进入 Context，完整结果另存以便审计。
5. MCP 统一了工具发现和调用方式，但不会自动提供 Agent 的决策能力。

## 证据边界

本轮没有请求在线 LLM，也没有重新运行依赖外部账户或 GUI 的正式 campaign。仓库里的历史 `validation` 不作为当前源码的实时验证结果，且不会提交到公开学习目录。
