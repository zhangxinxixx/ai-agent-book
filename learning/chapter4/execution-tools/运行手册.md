# 实验 4-4：执行工具

本实验研究的不是“让模型直接运行代码”，而是如何在模型与真实环境之间增加一层可控制、可验证、可观察的执行系统。

建议第一次只运行离线演示：

```powershell
conda activate agentbook
cd D:\Project\PythonpProject\agents\ai-agent-book\chapter4\execution-tools
python cli.py demo
```

这条命令不需要 API Key，不会调用日历或 GitHub，也不会修改当前项目目录；演示文件会写入系统临时目录。

> [!WARNING]
> `virtual_terminal` 最终会执行真实 Shell 命令。`--no-approval` 会关闭危险命令的 LLM 事前审批，只能在一次性临时工作区中使用，不能把它当作安全沙盒。

## 1. 实验要解决什么问题

普通 LLM 只能生成文本。Agent 要真正写文件、执行代码或调用外部系统，必须解决以下问题：

1. 谁把模型给出的参数转换成真实操作？
2. 如何限制文件只能写入指定工作区？
3. 如何在执行前拦截语法错误和危险操作？
4. 如何处理上千行输出，避免撑满模型上下文？
5. 如何把执行结果加工成 Agent 下一轮能使用的 Observation？
6. Docker 不可用时，代码到底在哪里运行？

本项目给出的答案是一套执行 Harness：

```text
调用者 / Agent
  -> CLI 或 MCP Server
  -> 工具路由
  -> 安全检查与自动验证
  -> 文件系统 / 本地进程 / Docker / 外部服务
  -> 结构化结果字典
  -> 调用者 / Agent 的下一轮决策
```

### 2.2 先做离线自检

```powershell
python cli.py --help

python -m pytest -q -p no:cacheprovider -o asyncio_mode=auto --basetemp .pytest-tmp
```

这三步分别验证：

- 六类工具能够注册；
- 文件、代码执行、终端和外部工具的测试能够通过。

### 2.3 运行端到端离线演示

```powershell
python cli.py demo
```

演示按以下顺序运行：

1. 写入合法 Python 文件，并执行语法校验；
2. 尝试写入语法错误文件，观察校验器如何阻止落盘；
3. 写入样本数据；
4. 用 `code_interpreter` 运行 Python 统计代码；
5. 用 `virtual_terminal` 运行 Shell 命令进行交叉验证；
6. 生成 1000 行输出，观察截断结果和完整输出文件路径；
7. 提交一个危险命令样例，观察离线 fail-safe 如何拒绝执行。

重点观察这些输出：

```text
success       操作是否成功
verification  自动语法校验是 passed、failed 还是 skipped
stdout        返回给 Agent 的标准输出；超长时只保留头尾
stderr        返回给 Agent 的标准错误
stdout_file   超长标准输出的完整落盘路径
stderr_file   超长标准错误的完整落盘路径
sandbox       实际执行环境，例如 docker 或 local-process
returncode    子进程退出码，0 通常表示成功
error_analysis 失败时的本地诊断；不代表已经请求 LLM
```

## 3. 常用命令

### 3.1 执行 Python 代码

```powershell
python cli.py code --language python --code "print(2 ** 10)"
```

从文件读取代码：

```powershell
python cli.py code --language python --file hello.py
```

### 3.2 执行 Shell 命令

```powershell
python cli.py shell "python --version"
```

### 3.3 写文件与编辑文件

建议显式指定一次性工作区：

```powershell
$demoWorkspace = Join-Path $env:TEMP "execution-tools-study"
New-Item -ItemType Directory -Force -Path $demoWorkspace | Out-Null

python cli.py --workspace $demoWorkspace write `
  --path notes.txt `
  --content "hello" `
  --overwrite

python cli.py --workspace $demoWorkspace edit `
  --path notes.txt `
  --search "hello" `
  --replace "你好"
```

### 3.4 全局开关

全局开关必须放在子命令前面：

| 参数 | 作用 | 风险或限制 |
| --- | --- | --- |
| `--workspace` | 覆盖 `WORKSPACE_DIR` | 文件工具只能访问该目录内部 |
| `--provider` | 覆盖 `PROVIDER` | 只在需要 LLM 时生效 |
| `--no-verify` | 关闭自动语法校验 | 错误代码可能直接进入执行阶段 |
| `--no-summarize` | 关闭 LLM 输出总结 | 长输出仍会截断并落盘 |
| `--no-approval` | 关闭危险操作审批 | 仅可用于受控临时环境 |

例如：

```powershell
python cli.py --workspace $demoWorkspace --no-summarize code --code "print('ok')"
```

## 4. 真实代码执行顺序

### 4.1 命令行总入口

```text
cli.py::main()
  1. build_parser() 定义参数
  2. parser.parse_args() 解析终端输入
  3. _apply_global_env() 写入本次运行的环境变量覆盖项
  4. args.func(args) 路由到具体子命令
  5. _build_tools() 延迟导入并创建工具实例
  6. 调用具体工具方法
  7. _print_result() 输出结构化 JSON
```

这里使用“延迟导入”很重要：`Config` 在模块导入时读取环境变量，因此必须先处理 `--workspace`、`--no-approval` 等参数，再导入工具模块。

### 4.2 `file_write` 写文件链路

```text
cmd_write()
  -> FileTools.write_file()
  -> _resolve_safe_path()：解析路径并检查工作区边界
  -> 文件已存在且 overwrite=False：拒绝
  -> 文件覆盖或其他敏感情况：按配置申请审批
  -> verify_code_syntax()：可识别代码时先校验
  -> Path.write_text()：真正写入文件
  -> 返回 success / path / bytes_written / verification
```

重点不是 `write_text()` 本身，而是写入前面的路径边界、覆盖控制与校验。

### 4.3 `code_interpreter` 代码执行链路

```text
cmd_code()
  -> ExecutionTools.code_interpreter()
  -> Python 本地 compile() 语法预校验
  -> 检测 eval / exec / subprocess / rm -rf 等危险模式
  -> 命中危险模式时请求 LLM 审批；无可用 LLM 时 fail-safe 拒绝
  -> LanguageExecutor.execute_code()
  -> 按 language 路由到 _run_python() / _run_javascript() / ...
  -> _run_command() 创建子进程并同时读取 stdout、stderr
  -> 超时则终止整个进程树
  -> truncate_and_persist() 处理超长输出
  -> 返回结构化 Observation
```

Python 的真实执行环境由 `multilang_executor.py::_run_python()` 决定：

```text
Docker 守护进程可用
  -> docker run --network none --memory 256m --cpus 1
  -> sandbox.kind = docker

Docker 不可用
  -> 当前机器上的 Python 子进程
  -> sandbox.kind = local-process
  -> sandbox.degraded = true
```

因此，看到 `local-process` 时只能说明代码执行成功，不能说明容器隔离已通过。

### 4.4 `virtual_terminal` 命令执行链路

```text
cmd_shell()
  -> ExecutionTools.virtual_terminal()
  -> 匹配危险命令模式
  -> 必要时申请审批
  -> subprocess.run(..., cwd=WORKSPACE_DIR, timeout=...)
  -> 捕获 returncode / stdout / stderr
  -> 截断并持久化超长输出
  -> 返回结构化 Observation
```

`cwd=WORKSPACE_DIR` 只限制命令的起始工作目录，不等于文件系统隔离。Shell 命令仍可能使用绝对路径访问工作区外部内容，所以不能依赖它替代 Docker、容器权限或操作系统沙箱。

### 4.5 超长输出如何加工

`execution_tools.py::truncate_and_persist()` 的处理顺序：

```text
原始 stdout / stderr
  -> 判断是否超过 200 行或 10000 字符
  -> 未超过：原样返回
  -> 超过：完整内容写入系统临时文件
  -> 上下文只保留前 50 行 + 后 50 行
  -> 返回落盘路径 stdout_file / stderr_file
```

这部分不依赖 LLM。Agent 可以先阅读头尾，再决定是否使用文件读取工具查看完整输出。

## 5. 谁负责什么

| 角色 | 本实验中的真实对象 | 职责 |
| --- | --- | --- |
| 调用者 | 人、Agent 或 MCP Client | 决定调用哪个工具以及传入什么参数 |
| Harness | `cli.py`、`server.py`、各 Tool 类 | 参数路由、安全检查、执行、结果加工 |
| Decision | 上游 LLM / Agent | 根据当前 Context 决定下一步 Action |
| Action | `file_write`、`code_interpreter` 等调用 | 对环境产生影响的动作 |
| Environment | 文件系统、Shell、Docker、Google、GitHub | 真正接受操作的外部环境 |
| Observation | 工具返回的结果字典 | `success`、`stdout`、`stderr`、`error` 等反馈 |
| Guard | 路径检查、审批、超时、输出阈值 | 限制风险和资源消耗 |
| Verifier | 语法校验、测试、正式实验验收 | 判断动作结果是否满足预期 |

五元素总结：

```text
State       = Config、WORKSPACE_DIR、当前目录、命令历史和本轮结果
Action      = 写文件、改文件、执行代码、执行命令、调用外部系统
Observation = success / stdout / stderr / error / verification / sandbox
Decision    = 上游 Agent；危险操作审批 LLM 只负责一个局部安全判断
Guard       = 工作区边界 + 危险模式审批 + 语法验证 + 超时 + 输出截断
```

## 7. 什么时候会请求模型

以下路径可能调用 LLM：

- 危险代码或危险命令的事前审批；
- 非 Python 代码的语法分析；
- 按配置对复杂输出进行总结；
- 部分外部系统操作的审批。

以下操作可以完全离线：

- `python cli.py list`；
- `python cli.py demo` 的默认路径；
- Python 的本地 `compile()` 语法校验；
- 长输出截断和完整内容落盘；
- 未触发危险模式的普通文件和本地执行操作。

如果需要测试真实 LLM 路径，复制配置模板，但不要覆盖已有 `.env`：

```powershell
Copy-Item env.example .env
```

然后只填写一个实际使用的 Provider 及其 Key。不要把 `.env`、Key、Token、Cookie 或授权头提交到 Git。

## 8. MCP Server 如何运行

启动标准输入输出形式的 MCP Server：

```powershell
python server.py
```

MCP Client 的调用过程是：

```text
session.initialize()
  -> list_tools 获取工具说明书
  -> call_tool(name, arguments) 发起工具调用
  -> server.py::handle_call_tool() 路由
  -> 具体 Tool 方法真正执行
  -> MCP 返回结构化结果
```

`server.py` 不负责决定“下一步该做什么”；它只负责公布工具、校验参数、路由调用并返回结果。循环决策仍在上游 Agent。

`google_calendar_add` 和 `github_create_pr` 会产生真实外部写入，不属于首次离线学习路径：

```text
google_calendar_add  需要 Google 凭据，并会创建真实日历事件

```

`run_experiment_4_4.py` 是正式验收入口，不是第一次运行入口。它还可能检查：

- Docker Python 容器隔离；
- Xvfb、Chromium、xdotool、FFmpeg 的真实桌面操作；

- Google Calendar、GitHub 和邮件等真实 Provider。

缺少这些外部环境时，正式实验会显示 blocked 或验收失败，这与本地核心工具代码能否运行是两回事。详细执行与证据边界见 [`实验逻辑流程.md`](实验逻辑流程.md)。

## 10. 常见问题

### `demo` 为什么不需要 API Key？

它默认关闭 LLM 输出总结，危险命令在没有可用 LLM 时按 fail-safe 拒绝。语法校验、代码执行、输出截断和落盘都可在本地完成。

### `success=true` 是否代表安全？

不是。它只表示本次工具动作按当前实现完成。还要检查 `sandbox`、`verification`、`returncode`，以及动作是否真的满足任务目标。

### 为什么有 `stdout_file`？

完整输出可能有几千行。直接放进 Agent Context 会浪费 Token，并挤掉真正重要的历史。返回文件路径后，Agent 可以按需读取。

### 为什么 Docker 不可用时还能执行 Python？

为了让开发环境继续可用，执行器会降级到本地 Python 子进程，并返回 `sandbox.degraded=true`。这是功能降级，不是容器验收通过。

### 为什么设置了 `WORKSPACE_DIR` 仍不能保证 Shell 安全？

它只控制进程的 `cwd`。Shell 仍能使用绝对路径或系统命令，因此真正的高风险执行还需要容器、最小权限、网络限制和人工审批。
