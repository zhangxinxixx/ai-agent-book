# 实验 2-10：上下文压缩策略实验总结

> 本文件保存可以公开的实验结果与分析。真实 API 原始日志、`.env` 和本地 `validation/` 不上传 GitHub。

## 1. 实验目标

本实验研究多轮 Agent 在工具结果不断累积时，怎样通过上下文压缩控制消息历史，并比较六种策略在以下方面的差异：

- 是否能完成任务；
- 上下文是否持续膨胀；
- 摘要是否保留后续决策需要的信息；
- 模型请求次数、token、耗时和 Provider 限额；
- 最终事实是否可追溯。

实验任务是查找并整理 OpenAI 联合创始人的当前职业归属。

## 3. 六种策略

| 策略 | 压缩方式 | 主要收益 | 主要风险 |
| --- | --- | --- | --- |
| `no_compression` | 所有工具结果保留原文 | 信息完整，适合作为基线 | 上下文、成本和延迟持续增长 |
| `individual` | 每个页面分别摘要后拼接 | 保留页面级边界 | 摘要请求多，跨页重复难去除 |
| `combined` | 同批页面合并后摘要一次 | 能跨页面去重 | 页面截断可能丢失末尾事实 |
| `context_aware` | 结合 query 与最近查询状态摘要 | 优先保留当前任务相关信息 | 额外调用多，错误状态会定向删错信息 |
| `citations` | 上下文感知摘要并保留来源 | 支持回查事实 | 引用增加体积，映射仍需验收 |
| `windowed` | 超过 80% 阈值后批量压缩历史工具消息 | 前期保留原文，后期集中减负 | 触发前仍可能出现 Context Rot |

## 4. 本地压缩演示

运行：

```powershell
python .\my_agent_test.py
```

观察到三次阈值触发：

| 触发轮次 | 压缩前 | 压缩后 | 字符减少 |
| --- | ---: | ---: | ---: |
| 第 4 轮 | 2,208 | 966 | 56.3% |
| 第 6 轮 | 2,052 | 880 | 57.1% |
| 第 9 轮 | 2,509 | 1,004 | 60.0% |

这个演示证明压缩改变的不是模型参数，而是下一轮模型能够看到的任务状态：

```text
旧轨迹原文 + 最近消息
→ 旧轨迹摘要 + 最近消息全文
→ 作为下一轮新的 Context
```

它只验证机制，不评估摘要语义质量。

## 6. 首个真实故障：压缩放大了请求数量

`context_aware` 的第一轮主模型返回了多个搜索调用，每个搜索结果又触发一次摘要请求：

```text
主 Agent 请求
→ 多个 search_web
→ 每个搜索结果分别请求摘要模型
→ Provider RPM 被快速消耗
→ 后续摘要或主 Agent 请求收到 HTTP 429
```

因此这次失败首先属于 Provider 请求预算与 Harness 调度问题，不能直接归因于上下文感知摘要的语义能力。

工程上需要让主 Agent 与 Compressor 共享统一的请求节流器、重试策略和请求计数器。

## 7. 为什么摘要可能比原文更长

本轮两次短结果摘要出现约：

```text
967 → 1,293 字符
967 → 1,274 字符
```

输入本来很短，而 `SUMMARY_MAX_TOKENS=500` 允许模型生成更长解释。当前代码没有：

- 短输入跳过摘要；
- 摘要不得长于原文；
- 按后续复用次数估算净收益。

真正应优化的是：

```text
净收益
= 后续多轮节省的上下文成本
- 本次摘要请求成本
- 摘要延迟
- 信息丢失风险
```

## 8. 当前指标的两个限制

### 8.1 `total_tokens` 漏算 Compressor

`AgentTrajectory.total_tokens_used` 只汇总主 Agent 请求。摘要模型使用的 prompt 和 completion token 没有进入该轨迹，所以压缩策略的实际端到端成本高于结果表。

后续应拆分记录：

```text
agent_prompt_tokens
agent_completion_tokens
compression_prompt_tokens
compression_completion_tokens
request_count
retry_count
rate_limit_count
```

### 8.2 字符压缩率口径不统一

本轮 `no_compression` 出现 139.3%。这不是语义内容真的膨胀了 39.3%，而是原始正文长度与格式化后工具消息长度使用了不同口径。

正式实验应对“实际送入下一轮模型的 tool message”使用同一个 tokenizer 统计前后 token。

## 9. 本轮可以确认的结论

1. 压缩由 Harness 在两次主模型请求之间执行，并改写下一轮 History。
2. 任务感知摘要不仅缩短文本，还尝试保留 query 和最近状态需要的信息。
3. 压缩本身会消耗模型请求、token、时间和 RPM，不能只计算压缩后的上下文。
4. 短工具结果不一定值得摘要，必须先判断净收益。
5. Provider 限流、轮次截断和上下文溢出是不同失败类型。
6. 压缩率低不代表答案正确，也不代表事实有来源支撑。

## 10. 本轮不能得出的结论

- 不能比较六种策略的最终排名；
- 不能证明 `context_aware` 一定优于 `no_compression`；
- 不能验证实时职业归属事实；
- 不能验证真正的 128K 上下文溢出；
- 不能把当前主 Agent token 当作端到端总成本；
- 不能把字符压缩率当作 token 压缩率。

## 11. 下一轮实验

先修改 Harness：

1. 主请求与摘要请求共享 RPM 节流和指数退避；
2. 补齐 Compressor token 与请求次数；
3. 统一前后 token 统计口径；
4. 加入短输入跳过摘要和反向膨胀保护。

再按两个阶段执行：

```text
阶段 A
固定大体积 mock 工具结果
→ 验证阈值、批量压缩、防重复标记和指标

阶段 B
固定模型、温度、任务、搜索结果和最大轮次
→ 先比较 no_compression、context_aware、windowed
→ 测量链可靠后再扩展到全部六种策略
```

每种策略至少重复 3 次，并分别报告完成率、事实保留、来源可追溯、端到端 token、时间和失败类型。

## 一句话总结

> 上下文压缩的本质，是 Harness 在两次模型决策之间把低密度历史替换成高密度任务状态；只有信息保留、端到端成本、请求预算和测量口径同时成立时，它才是真正有效的压缩。
