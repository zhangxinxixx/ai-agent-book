# 实验 2-10：上下文压缩策略对比

本目录演示 Agent 在多轮工具调用中如何压缩不断增长的上下文，并比较六种策略在任务完成、上下文体积、模型请求次数、延迟和信息保留方面的差异。

实验任务是：搜索并整理 OpenAI 联合创始人的当前职业归属。

返回[第 2 章目录](../README.md)。原理说明见[《深入理解 AI Agent》第 2 章：上下文压缩策略](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter2.md#上下文压缩策略)。代码调用链和消息状态变化见[实验 2-10 执行流程](<实验逻辑流程.md>)，本轮结果与限制见[实验 2-10 实验总结](<实验总结.md>)。

> [!IMPORTANT]
> 不要第一次就运行全部六种策略。压缩策略会产生额外的模型摘要请求，完整实验可能耗时很长并触发 Provider RPM 限制。请按本文的“建议运行顺序”逐步执行。

## 2. 当前代码结构

| 文件 | 直接职责 |
| --- | --- |
| `config.py` | 读取 Provider、模型、窗口预算和压缩参数 |
| `web_tools.py` | 执行 Serper 搜索和网页抓取；无 Key 时返回 mock 数据 |
| `compression_strategies.py` | 定义六种策略并生成 `CompressedContent` |
| `agent.py` | 维护消息历史、执行工具、记录 `AgentTrajectory` |
| `experiment.py` | 运行策略、汇总指标并保存 JSON |
| `run_all_strategies.py` | 保存详细 `.log` 和策略结果 JSON |
| `benchmark_compression.py` | 规则型压缩基准模块，不是六策略在线实验入口 |

核心循环：

```text
当前消息历史
→ kimi-k3 决定调用工具
→ WebTools 返回原始搜索结果
→ ContextCompressor 按策略处理结果
→ 原文或摘要加入消息历史
→ kimi-k3 继续决策
→ 最终答案或 Harness 强制停止
```

## 6. 六种策略怎么区分

| 别名 | 完整策略名 | 什么时候压缩 | 主要观察点 |
| --- | --- | --- | --- |
| `no_compression` | `NO_COMPRESSION` | 从不压缩 | 上下文增长和溢出基线 |
| `individual` | `NON_CONTEXT_AWARE_INDIVIDUAL` | 每个页面分别摘要 | 摘要请求次数、重复信息 |
| `combined` | `NON_CONTEXT_AWARE_COMBINED` | 同批页面合并摘要 | 跨页面去重和输入截断 |
| `context_aware` | `CONTEXT_AWARE` | 每次搜索后 | query 与最近状态是否保留了关键信息 |
| `citations` | `CONTEXT_AWARE_CITATIONS` | 每次搜索后 | 摘要事实能否回溯来源 |
| `windowed` | `WINDOWED_CONTEXT` | 最近 prompt 超过窗口预算的 80% 后 | 阈值触发、批量压缩、`[COMPRESSED]` 防重复 |

压缩发生在两次主模型请求之间：Harness 用压缩结果替换或包装工具消息，然后把新的消息历史发送给下一轮模型。

## 8. 怎样阅读结果

结果 JSON 的核心指标：

| 字段 | 当前含义 | 注意事项 |
| --- | --- | --- |
| `success` | 是否生成了最终答案 | 不等于答案正确或事实有证据 |
| `iterations` | 实际进入 Agent 循环的轮次 | 达到上限可能没有最终答案 |
| `tool_calls` | Agent 执行的工具调用数量 | 一轮可以包含多个工具调用 |
| `context_overflows` | 超过演示窗口阈值的计数 | mock 数据较短时可能始终为 0 |
| `execution_time` | 单策略运行时间 | 同时受网络、模型和限流影响 |
| `total_tokens` | 当前 `AgentTrajectory` 记录的主 Agent token | 尚未包含 Compressor 摘要请求 token |
| `compression_ratio` | 压缩后字符数 / 原始字符数 | 当前不是 tokenizer 级 token 压缩率 |
| `final_answer_length` | 最终答案字符数 | 长度不能代表正确性 |

必须把三件事分开判断：

```text
Completed：是否生成最终答案
Correct：答案是否正确
Grounded：答案是否由可追溯证据支持
```

| --- | ---: | ---: | ---: | ---: | --- |
| `context_aware` | 3 | 4 | 2,530 | 85.8% | HTTP 429，未完成 |
| `no_compression` | 3 | 8 | 5,158 | 139.3% | 达到轮次上限，未完成 |

证据：

```text

validation\pilot_20260919_no_compression_kimi_k3\evidence.json
```

这两组是链路 pilot，不是六策略排名依据。它们揭示了三个需要先修正的问题：

1. `context_aware` 的额外摘要调用会快速消耗 RPM。
2. 短结果可能被摘要得更长，本轮出现过约 `967 → 1,293` 字符。
3. 当前无压缩字符比率可能超过 100%，因为前后 JSON 序列化口径并不完全一致。

## 10. 常见问题

### 为什么没有 `SERPER_API_KEY` 也能运行？

`web_tools.py` 会退回内置 mock 数据。这样能观察 Agent Loop 和压缩控制流，但不能验证实时网页事实。

### 为什么出现 HTTP 429？

上下文感知、逐页摘要和带引用摘要都会产生额外模型请求。当前代码没有让主请求和摘要请求共享统一的 RPM 节流器，因此可能超过 Provider 限制。

处理原则：

- 停止连续重试，等待 Provider 时间窗口恢复。
- 先用 `no_compression` 或单轮 `context_aware` 做冒烟测试。
- 不把 HTTP 429 归因于策略的语义效果。
- 完整对比前先给 Harness 增加统一请求节流和重试记录。

### 为什么 `success=false`，但没有异常？

通常是 `max_iterations` 用完后仍未生成最终答案。它属于 Harness 截断，不是 Provider 错误。

### 为什么压缩后反而更长？

输入本来很短，而 `SUMMARY_MAX_TOKENS` 允许模型生成更长的解释。当前实现没有“短输入跳过摘要”或“摘要不得长于原文”的保护。

### 为什么 `compression_ratio` 大于 100%？

当前指标按字符统计，而且部分路径使用的 JSON 格式不同。它首先是测量口径问题，不应直接解释成语义膨胀。

### 为什么没有触发 128K 溢出？

mock 搜索结果很短，少量轮次不足以制造真正的长上下文压力。要验证溢出，需要固定的大体积 mock 数据或真实网页结果。

### 为什么不建议直接跑全部六种？

完整对比不仅包含主 Agent 请求，还包含大量摘要请求。在当前 RPM 条件下，直接全跑更可能得到一组限流失败，而不是有效策略对照。

## 11. 关键配置

| 配置 | 默认值 | 作用 |
| --- | ---: | --- |
| `MODEL_NAME` | `kimi-k3` | 主 Agent 和摘要使用的模型 |
| `MODEL_TEMPERATURE` | `0.3` | 采样温度 |
| `MODEL_MAX_TOKENS` | `8192` | 单次模型输出预算 |
| `MAX_ITERATIONS` | `50` | Agent 最大轮次 |
| `MAX_WEBPAGE_LENGTH` | `50000` | 单页内容截断长度 |
| `SUMMARY_MAX_TOKENS` | `500` | 摘要输出预算 |
| `CONTEXT_WINDOW_SIZE` | `128000` | 实验人为设置的上下文预算 |

`CONTEXT_WINDOW_SIZE=128000` 是为了让压缩和溢出更容易被观察，不代表 `kimi-k3` 的真实最大窗口只有 128K。

## 13. 完成一次实验的最低验收标准

一次“已完成”的策略实验至少需要同时记录：

- 固定的模型、温度、任务、搜索数据和最大轮次。
- 主 Agent 与 Compressor 各自的请求次数和 token。
- 是否完成、是否正确、是否有来源证据。
- 压缩前后使用同一口径计算的 token。
- HTTP 429、超时、重试、轮次截断和上下文溢出的分类。
- 原始 evidence 路径与 SHA-256。

在这些条件补齐以前，本目录当前结果应标记为“链路已验证，六策略对照未完成”。
