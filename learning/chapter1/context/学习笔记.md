# 上下文感知 Agent 学习笔记

> 配套《深入理解 AI Agent》第 1 章实验 1-1：上下文的关键作用。

← [返回学习目录](README.md) · [查看实验逻辑流程](实验逻辑流程.md) · [查看实验总结](实验总结.md)

## 1. 这个实验在研究什么

Agent 不只是把用户问题发给模型。它还要把前几轮消息、工具调用和工具结果一起交给模型，模型才能知道：

- 用户要完成什么任务；
- 自己前面做过什么；
- 工具返回了什么；
- 下一步应该继续调用工具，还是给出最终答案。

实验会有意删除其中一类信息，再观察 Agent 的行为变化。这种对比方法叫作**消融实验**（Ablation Study）。

## 2. Agent 的基本执行过程

一次任务的主流程是：

```text
用户任务
  -> 组成 messages
  -> 请求模型
  -> 模型决定调用工具或直接回答
  -> 本地执行工具
  -> 把工具结果加入 messages
  -> 再次请求模型
  -> 得到最终答案或达到最大轮数
```

这里最重要的是区分三类内容：

| 内容 | 含义 |
| --- | --- |
| `tool_calls` | 模型提出的工具调用请求，例如“把欧元换算成美元” |
| `tool` result | 工具真正返回的数据，例如换算后的金额 |
| `conversation_history` | 下一轮请求模型时携带的历史消息 |

工具调用和工具结果不是一回事。模型即使记得自己调用过工具，如果看不到工具结果，仍然无法继续计算。

## 3. 五种上下文模式

| 模式 | 删除什么 | 模型还能看到什么 | 常见表现 |
| --- | --- | --- | --- |
| `full` | 什么都不删 | 完整历史、工具定义、工具调用和结果 | 正常完成任务，作为对照组 |
| `no_history` | 前几轮历史消息 | system 提示词和当前用户任务 | 忘记已经做过的事，容易重复调用工具 |
| `no_tool_results` | 工具返回的具体内容 | 工具调用记录还在 | 知道调用过工具，却不知道结果，只能重试或停下 |
| `no_tool_calls` | 请求中的工具定义 | 普通文本消息 | 无法调用工具，可能拒绝回答，也可能给出没有依据的数字 |
| `no_reasoning` | 写入历史的推理文本 | 工具调用和工具结果仍然保留 | 仍可能完成任务，但多轮计算更容易出现单位或步骤错误 |

需要特别注意：

- `no_tool_calls` 中没有工具调用，是因为程序根本没有向模型提供工具，不能据此判断模型能力强弱。
- `no_reasoning` 只删除写入下一轮历史的 `reasoning_content`，并没有禁止模型在当前轮进行推理。
- 单次实验会受模型采样影响。一次成功或失败不能直接推广到所有模型和任务。

## 4. 代码如何实现上下文删减

核心代码在 [agent.py](code/agent.py)：

1. `ContextMode` 定义五种模式。
2. `execute_task()` 负责“模型 -> 工具 -> 再请求模型”的循环。
3. `_prepare_messages_for_api()` 决定下一轮向模型发送哪些历史消息。
4. `_prepare_assistant_message()` 决定 assistant 消息写入历史时是否保留推理内容。
5. `execute_task()` 在工具执行后决定写入真实结果，还是隐藏结果内容。

其他重要文件：

| 文件 | 作用 |
| --- | --- |
| [main.py](code/main.py) | 命令行入口和交互模式 |
| [run_experiment_1_1.py](code/run_experiment_1_1.py) | 依次运行不同模式并保存实验结果 |
| [grounding.py](code/grounding.py) | 检查回答中的数字是否有工具结果作为依据 |

更完整的调用顺序和关键源码位置见[实验逻辑流程](实验逻辑流程.md)。

## 5. 怎样判断实验结果

`Completed=True` 只表示 Agent 已经停止循环并返回文本，不表示答案一定正确。

应优先查看 `outcome`：

| `outcome` | 含义 |
| --- | --- |
| `correct` | 给出了最终答案，并且关键数字正确 |
| `unsupported_numbers` | 回答中出现了任务和工具结果都没有提供的数字 |
| `no_unsupported_numbers` | 没有编造数字，但也不一定完成了任务 |
| `incorrect` | 有可用的工具结果，但最终答案仍然错误 |
| `no_terminal_response` | 达到最大轮数或运行报错，没有正常结束 |

判断一个模式是否真正生效，还要看实际请求中的消息和工具字段，不能只看命令行参数名称。

## 6. 从实验中学到什么

### 历史消息让 Agent 知道自己做过什么

删除历史后，模型每一轮都像第一次看到任务，容易反复执行相同操作。

### 工具结果是继续推理的事实依据

模型知道“调用过工具”还不够。只有看到工具返回的数据，才能进行后续计算和判断。

### 生成了答案不等于答案可信

模型可能在没有工具的情况下直接给出一个看起来完整的答案。因此还要检查金额、日期等关键事实是否来自实际观察结果。

### 推理记录有助于保持多轮任务一致

在涉及金额单位、换算和多步计算时，保留推理过程有助于模型维持前后一致。但是否保留推理不是唯一影响因素，不能根据一次结果下结论。

### 对照实验必须记录实际输入和输出

只有保存每轮真实发送的消息、工具调用、工具结果和最终判定，才能确认删减模式真的生效，并解释失败原因。

具体的实测结果和各模式表现见[实验总结](实验总结.md)。

## 7. 推荐源码阅读顺序

1. `agent.py` 中的 `ContextMode`：先认识五种模式。
2. `agent.py` 中的 `execute_task()`：理解 Agent 主循环。
3. `_prepare_messages_for_api()`：观察 `no_history` 如何删掉历史。
4. `_prepare_assistant_message()`：观察 `no_reasoning` 如何删掉推理文本。
5. `execute_task()` 的工具结果写回部分：观察 `no_tool_results` 如何隐藏工具结果。
6. `run_experiment_1_1.py`：理解实验如何运行和判定。
7. `grounding.py`：理解为什么“返回了文本”不等于“答案有依据”。
