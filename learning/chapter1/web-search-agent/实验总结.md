## 1. 实验目标

理解 Web Search Agent 如何完成下面的反馈闭环：

```text
LLM Decision
→ web_search Tool Call
→ Formula Fiber 执行搜索
→ Search Result 写回 Context
→ LLM 根据新 Observation 再次决策
```

本实验重点不是实现搜索引擎，而是确认模型决策、Harness 执行、工具反馈、状态更新和停止条件之间的责任边界。

## 3. 主要观察

### 观察 1：模型负责决策，Harness 负责执行

模型返回 `web_search` Tool Call，但不会直接执行 Python 或 HTTP 请求。`WebSearchAgent` 解析 Tool Call，调用 Formula Fiber，再把结果组装成 `role=tool` 消息。

### 观察 2：Observation 必须进入模型可见 Context

搜索结果只有写入 `conversation_history`，才能影响下一轮 Query。单独写进 `trace` 只能帮助人阅读，不能替代模型输入。

### 观察 3：工具声明与工具执行是两步

`_get_tools()` 先取得标准 `web_search` Schema；模型依据 Schema 生成参数；`_execute_formula()` 再执行具体搜索。把两步混为一谈，会误判请求失败发生在哪一层。

### 观察 4：完成和成功不是一回事

产生 Final Answer 只能说明循环结束。正式实验还要求工具声明、Chat、Fiber、搜索 Action、来源链接和指定事实能够互相对齐，并最终满足 `validate()` 的验收规则。

## 4. 实验结论

1. Web Search Agent 的核心是 `Observation → State Update → Next Decision`，不是简单调用一次搜索接口。
2. LLM、Harness、Tool 和 Verifier 的职责必须分开：模型做决定，Harness 执行并维护状态，Tool 提供外部信息，Verifier 判断结果是否可信。
3. `conversation_history`、`trace` 和 `api_turns` 服务于不同对象，不能互相替代。
4. 最大轮次、超时和错误分类是运行边界；`acceptance.passed` 是结果验收，两者不是同一件事。
5. 当前离线测试已经验证本地控制逻辑，但真实联网能力仍需要单独运行并保留 Evidence。

## 5. 局限与待完成事项

- 本轮没有调用付费模型，也没有测试 Moonshot 当前在线状态。
- `42 passed` 是 2026-09-20 的公开代码快照结果；测试数量变化后应以新的运行结果为准。
- 离线 Demo 是固定教学轨迹，不能证明模型真的根据搜索结果改变了策略。
- 真实搜索结果可能受到 Provider 状态、权限、速率限制、网络和信息时效影响。

3. 运行正式实验脚本，确认 `acceptance.passed=True`、退出码为 `0`，并保存独立的 `evidence.json` 与 SHA-256。

## 6. 一句话总结

> Web Search Agent 不是“模型自己上网”，而是模型根据 Context 提出搜索 Action，Harness 执行工具并把结果作为 Observation 写回 Context，再由模型根据新信息继续决策，直到正常结束或触发运行边界。
