# User Memory 实验总结

## 实验结论

这个实验展示了一个比“保存全部聊天记录”更合理的长期记忆方案：

```text
原始对话 -> ConversationHistory
新对话 -> 后台 Agent 分析 -> 受控记忆工具 -> MemoryManager
下一次请求 -> 重新加载长期 Memory
```

最核心的设计是把原始证据和提炼后的状态分开。原始 History 用于追溯和重新处理；Memory 用于跨 Session 个性化，并允许新增、更新和删除。

## 本次整理包含什么

- 当前本地版本的 23 个顶层 Python 文件；
- 配置模板、依赖文件、Provider 说明和测试文件；
- 运行手册、学习笔记、实验逻辑流程；
- 已核对的静态架构图。

没有上传 `.env`、真实对话、用户记忆、日志、评测原始数据、缓存或运行轨迹。

## 历史四模式观察

已有历史证据比较了 60 个用例和四种 Memory Mode：`notes`、`enhanced_notes`、`json_cards`、`advanced_json_cards`。

历史结果中，`enhanced_notes` 在那批用例上取得最高综合通过率和平均奖励，同时 Token 与平均调用延迟最低。这个结果说明：

- 更复杂的 schema 不一定带来更好效果；
- Prompt 和信息组织方式可能比字段数量更重要；
- 结构化格式不能自动解决事实错误、实体冲突和过期信息。

这些是历史环境下的观察，不能当作当前代码、当前模型或所有业务场景的普遍结论。

## 做对的地方

1. **原始历史和长期记忆分层**：既能审计，也能控制上下文体积。
2. **前台只读、后台可写**：降低回答过程中随意改写长期状态的风险。
3. **使用 Tool Call 修改记忆**：每次状态变化都能形成明确的动作和结果。
4. **支持不同记忆表示**：便于比较文本笔记与结构化卡片的取舍。
5. **跨 Session 重新加载**：验证了长期状态与当前会话状态的生命周期不同。

## 仍然存在的问题

1. `processed_turn_ids` 和处理计数只在进程内，无法保证 exactly-once。
2. 后台失败后缺少持久化重试队列，可能漏处理，也可能在重启后重复处理。
3. JSON 文件缺少生产级事务、并发控制、权限隔离和审计机制。
4. 在线路径没有独立事实 Verifier，写盘成功不等于记忆正确。
5. Memory 与原始对话都可能包含隐私信息，需要保留期限、删除机制和访问控制。
6. 多用户、多实体和偏好变化仍需要更严格的冲突处理策略。

## 怎样判断实验真正跑通

不能只看模型回复“我记住了”。至少应同时看到：

- 原始 user / assistant 轮次写入 `ConversationHistory`；
- 后台模型返回了记忆 Tool Call；
- Harness 执行工具并返回匹配的 Tool Result；
- 长期 Memory 文件发生预期变化；
- `reset` 后新 Session 没有直接携带旧 Session 原文；
- 新会话能够从长期 Memory 恢复正确事实。

## 最终收获

用户长期记忆的重点不是“存得多”，而是：

- 哪些信息值得保存；
- 谁有权写入；
- 新事实怎样更新旧事实；
- 错误信息怎样删除；
- 下一次任务怎样只取回真正相关的内容；
- 每条结论能否追溯到原始证据。

一句话总结：

> 长期记忆是由原始对话提炼、通过受控动作维护、在后续会话按需加载的持久状态，而不是无限增长的聊天记录。
