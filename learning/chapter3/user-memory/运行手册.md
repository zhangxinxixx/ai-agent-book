# 实验 3-1 / 3-2：用户长期记忆

这个实验演示 Agent 如何把“当前会话上下文”和“跨会话长期记忆”分开管理。

它不是简单地把全部聊天记录永久塞进提示词，而是使用两条职责不同的链路：

```text
前台对话链
用户输入
→ ConversationalAgent 读取当前会话历史
→ 读取已经持久化的长期记忆
→ 请求模型并返回回答
→ ConversationHistory 保存本轮原始对话

后台记忆链
ConversationHistory 中的新对话
→ BackgroundMemoryProcessor 判断是否触发
→ UserMemoryAgent 分析值得长期保存的信息
→ add/update/delete_memory 工具
→ MemoryManager 写入磁盘
→ 后续对话重新加载并使用长期记忆
```

最重要的学习目标是：

> 当前对话历史是正在执行的短期状态；长期记忆是从历史中提炼、可跨会话复用的持久状态。二者生命周期、内容粒度和写入责任都不同。


### 第三步：运行交互实验

```powershell
python .\main.py `
  --mode interactive `
  --user learner_01 `
  --memory-mode notes `
  --provider kimi `
  --conversation-interval 1
```

交互命令：

| 命令 | 作用 |
|---|---|
| `memory` | 重新加载并显示当前长期记忆 |
| `process` | 立即处理尚未处理的对话 |
| `save` | 手动触发最近对话的记忆处理 |
| `reset` | 新建会话；不会删除长期记忆 |
| `quit` / `exit` | 停止后台线程并退出 |

若只想观察当前会话、不运行后台记忆抽取：

```powershell
python .\main.py --mode interactive --memory-mode notes --no-background-processing
```

### 第四步：观察跨会话记忆

在第一个会话中输入：

```text
我正在学习 AI Agent，习惯使用 Windows PowerShell。
```

等待后台处理或输入 `process`，再执行：

```text
memory
reset
```

新会话中再问：

```text
你记得我的学习主题和终端偏好吗？
```

观察重点不是回答听起来是否自然，而是：

1. 原始对话写入了哪个 history 文件；
2. 后台 Agent 是否真的调用了记忆工具；
3. 长期记忆文件是否新增或更新；
4. 新会话的提示词是否通过长期记忆获得旧信息，而不是直接读取旧会话全文。

## 4. 四种记忆模式

| 参数 | 存储形式 | 适合观察什么 |
|---|---|---|
| `notes` | 单条事实笔记 | 最容易理解 add/update/delete |
| `enhanced_notes` | 带更多上下文的段落笔记 | 信息完整度与冗余 |
| `json_cards` | 分层 JSON | 类别、字段和值的结构化维护 |
| `advanced_json_cards` | 带人物、关系和背景的卡片 | 多人物信息隔离与消歧 |

切换示例：

```powershell
python .\main.py --mode interactive --user learner_json --memory-mode json_cards
python .\main.py --mode interactive --user learner_advanced --memory-mode advanced_json_cards
```

四种模式都把数据写入 `data/memories/<user_id>_memory.json`，但文件内部结构不同。比较模式时应使用不同的测试 `user_id`，不要让一种模式直接读取另一种模式生成的文件。

## 5. 一次对话的真实执行顺序

入口位于 `main.py::interactive_mode()`：

```text
1. 创建 ConversationalAgent
2. 创建 BackgroundMemoryProcessor
3. 启动后台线程
4. 用户输入普通消息
5. ConversationalAgent.chat()
6. _get_memory_context() 重新读取长期记忆
7. 只读取当前 session_id 对应的原始会话轮次
8. 临时组装本轮 API messages
9. 模型生成回答
10. 原始 user/assistant 写入 ConversationHistory
11. 主线程增加 conversation_count
12. 后台线程满足间隔后读取新对话
13. UserMemoryAgent 决定 add/update/delete_memory
14. MemoryManager 持久化
15. 下一轮 chat() 重新加载后看到新记忆
```

关键点：`ConversationalAgent` 只读取长期记忆，不直接负责写入；写入由后台处理器中的 `UserMemoryAgent` 通过工具完成。

## 6. 短期上下文与长期记忆

| 对比项 | 当前会话上下文 | 长期记忆 |
|---|---|---|
| 真实对象 | `self.conversation`、当前会话轮次 | `MemoryManager` 管理的数据 |
| 保存内容 | 本轮对话原文和消息角色 | 提炼后的事实、偏好、关系或卡片 |
| 生命周期 | 当前会话为主 | 跨会话持久化 |
| 写入者 | `ConversationalAgent.chat()` | 后台 `UserMemoryAgent` 的记忆工具 |
| 模型可见方式 | 消息历史直接进入请求 | `_get_memory_context()` 转成文本后临时注入 |
| reset 影响 | 创建新会话、清空前台消息 | 不删除长期记忆 |

为什么必须分开：

- 把全部旧对话放入每次请求，会让上下文不断膨胀；
- 原始对话包含寒暄、错误和过期内容，不等于可长期信任的记忆；
- 长期记忆需要增删改、去重、冲突处理和用户隔离；
- 前台回答和后台记忆抽取有不同延迟与可靠性要求。

## 7. 核心状态怎样变化

```text
初始化
conversation = [system]
session_id = 新标识
长期记忆 = 从磁盘加载

完成第 1 轮对话
conversation += [user, assistant]
ConversationHistory += 一条带 session_id 的对话记录

后台处理完成
processed_turn_ids += 本轮 ID
MemoryManager += 新增/更新后的长期记忆

reset 后
conversation = [system]
session_id = 新标识
长期记忆保持不变
```

`processed_turn_ids` 只在当前后台处理器进程中防止重复处理；它不是永久的全局幂等记录。

## 11. 常见问题

### `reset` 为什么没有清空长期记忆？

`reset_session()` 只创建新的 `session_id` 并重置当前对话。这正是实验要展示的“会话短期状态”和“跨会话长期记忆”分离。

### 为什么刚说完的信息还没出现在 `memory` 中？

长期记忆需要后台处理。等待触发间隔，或输入 `process`。还要检查后台 Agent 是否成功调用了记忆工具。

如果使用 `--no-background-processing`，前台回答仍会写入 ConversationHistory，但当前进程不会把它提炼成长时记忆；需要重新启用后台处理或使用独立处理命令。

### 为什么前台智能体不直接写长期记忆？

前台链路优先保证回答延迟和对话连贯；后台链路负责筛选、冲突处理和持久化，避免把每句话都无条件当成事实。

### 为什么日志里的提示词很长？

`verbose=True` 会输出注入的 memory context。日志可能包含个人信息，只应用于本地学习，不要上传。

### 怎样判断实验真的成功？

不能只看模型说“我记住了”。至少要同时检查：原始对话历史、记忆工具调用结果、长期记忆文件变化，以及新会话是否从长期记忆恢复信息。
